1
Pergunta provável · “por que a lista filtrada não deve ser armazenada como segunda fonte de verdade?”

Guarde os critérios. Calcule a lista.

Seu estado guarda as 9 tarefas originais e os critérios (busca, status, prioridade, ordenação). Ele não guarda uma lista tarefasFiltradas.

Se guardasse, existiriam duas listas para manter combinando. Uma hora o filtro muda, alguém esquece de recalcular a segunda, e a tela mostra uma coisa enquanto o estado diz outra.

Por isso a lista visível é calculada na hora por derivarVisiveis(estado) toda vez que a tela desenha — e jogada fora em seguida. Uma coisa que não é guardada não tem como ficar desatualizada.

Analogia. Cardápio e pedido. O cardápio (todas as tarefas) e o que o cliente pediu (os critérios) são a fonte. O prato na mesa (a lista visível) é feito na hora a partir dos dois. Você não guarda pratos prontos na geladeira “para o caso de o pedido não mudar”.

Experimento duas fontes de verdade

A · guardando tarefasFiltradas

B · derivando a cada render

Clique em “filtrar”, depois em “mudar filtro” e compare as duas caixas.
respostaPorque duas cópias podem discordar. Derivando a cada ciclo, a lista está sempre certa por construção — ela nem é guardada.
2
Pergunta provável · “por que sort() pode alterar o array original?”

sort() não devolve uma cópia. Ele reordena o que já existe.

Muita gente acha que sort() funciona como filter(): você chama, recebe um array novo e o antigo fica igual. Não é assim. sort() reordena o próprio array (“in place”) e devolve ele mesmo.

Se o seu código fizesse estado.tarefas.sort(), a ordem em que as tarefas vieram do JSON seria perdida para sempre. A opção “Ordem original” do select deixaria de existir — não há mais original para voltar.

Por isso o código ordena uma cópia: [...visiveis].sort(). O [...] (spread) cria um array novo; o sort() mexe só nele.

Analogia. É a diferença entre pedir a alguém “me passa uma cópia da lista em ordem alfabética” e “reescreve a lista em ordem alfabética”. Na segunda, a ordem antiga acabou.
// mexem no original (mutadores):
sort  reverse  push  pop  shift  unshift  splice
// devolvem um array novo:
filter  map  slice  concat  [...spread]  toSorted

Experimento ordenar por prazo

estado.tarefas (ids na ordem do JSON)
visiveis (o que vai para a tela)
Aperte um botão e olhe a linha de cima.
respostaPorque sort() ordena no próprio array e não cria cópia. Ordenando uma cópia ([...visiveis].sort()), a ordem original sobrevive.
3
Pergunta provável · “qual é a sequência evento → estado → derivação → renderização?”

O evento não desenha nada. Ele só muda dados.

Quando você digita na busca, o ouvinte faz exatamente duas coisas: escreve no estado (estado.busca = 'py') e chama atualizar(). Ele não filtra, não esconde cartão, não lê outro controle.

atualizar() chama renderizar(estado) — o único lugar que desenha. Lá dentro, em ordem: deriva a lista uma vez, desenha os cartões, escreve “N de M” e a mensagem, e sincroniza os controles com o estado.

Como tudo sai do mesmo objeto, a tela e os controles nunca discordam. E a ordem em que você mexe nos filtros não importa: o que conta é o valor atual do estado, não o histórico de cliques.

Analogia. Um placar de estádio. O juiz (evento) não pinta o placar: ele anota o gol na súmula (estado). O painel (tela) é redesenhado a partir da súmula. Se dois painéis mostram números diferentes, o problema não é o painel — alguém escreveu fora da súmula.

Detalhe que cai junto: “Limpar filtros” é type="button", não reset. reset limparia só os campos e o estado ficaria com os filtros antigos. O botão restaura o estado; a renderização traz os campos junto.

4
Pergunta provável · “por que zero resultados não é erro?”

Erro é quando a busca dos dados falhou. Zero resultados é a busca tendo funcionado.

Erro é a rede cair, o servidor responder 404/500 ou o JSON vir quebrado. A obtenção falhou. Isso cai no catch de iniciar(), em main.js, e vira estado.carregamento = 'erro'.

Zero resultados é diferente: os dados chegaram certinhos, as 9 tarefas estão no estado, só que a busca “zzz” não bate com nenhuma. Quem decide isso é a lista derivada: visiveis.length === 0, dentro de renderizar(), no caminho de sucesso. Nunca passa perto de um catch.

E tem uma terceira: origem vazia — o JSON veio válido, mas com zero tarefas. Também não é erro. Três situações, três mensagens diferentes na tela.

Analogia. Você liga para a pizzaria. “Não atende” é erro. “Atendeu, mas não tem a pizza que você quer” não é erro — é zero resultados. Tratar os dois igual seria mentir para o cliente.

Experimento quem decide?

Clique numa situação.
respostaErro é falha de obtenção (catch). Zero resultados é decidido pela lista derivada (visiveis.length === 0) no caminho de sucesso — os dados vieram, os critérios não acharam nada.

Pergunta provável · “por que a versão local funciona e a URL publicada retorna 404?”

Três motivos. Todos escondidos pelo seu computador.

a) Caminho absoluto. /js/main.js funciona no localhost porque a raiz do servidor é a pasta do projeto. No Pages, a raiz do domínio é andreybueno-git.github.io/ e o projeto vive em /front-end/ — a barra inicial aponta para um lugar que não existe. Por isso o seu HTML usa caminhos relativos: js/main.js, dados.json, styles.css.

b) Maiúscula e minúscula. Windows e macOS não diferenciam: Styles.css abre styles.css. O servidor do Pages roda Linux, que diferencia. Local abre, publicado dá 404.

c) Arquivo fora do Git. Está no seu disco, então funciona local. Mas não foi commitado (ou está no .gitignore), e o Pages só publica o que está no repositório.

Como verificar. Janela anônima → DevTools → Network → recarregar → tudo 200. Console vazio. Se algo dá 404, olhe o caminho na coluna “Name” e compare letra por letra com o arquivo no GitHub.
